## 一、项目背景与目标

### 1.1 业务背景

钢铁行业交易具有**大宗、高频、多品规、多批次**的特点，买卖双方在一个结算周期内可能产生数十甚至数百笔交易。传统对账依赖线下 Excel 传递、人工核对，存在以下痛点：

| 痛点 | 影响 |
|------|------|
| 对账周期长 | 平均 5-10 个工作日完成一轮对账 |
| 差异排查难 | 多品规/多批次场景下人工比对效率极低 |
| 沟通成本高 | 电话、微信、邮件多渠道反复沟通 |
| 确认无凭证 | 双方确认结果缺乏法律效力 |
| 催收脱节 | 对账完成后催款依赖人工跟进，容易遗漏 |
| 买方能力参差 | 部分买方无 ERP 系统，只能手工管理，对账全靠 Excel/纸质 |
| 期中付款混乱 | 对账周期内买方已支付部分款项，但对账时难以准确抵扣 |

### 1.2 项目目标

构建一套 **"ERP 驱动 + 多模式适配、模板化生成、自动化比对、电子签章确认、智能催收闭环"** 的线上对账系统：

| 目标 | 指标 |
|------|------|
| 对账效率 | 对账周期从 5-10 天缩短至 1-2 天 |
| 异议处理 | 异议处理效率提升 60% 以上 |
| 并发能力 | **支持 10,000 人同时在线对账** |
| 买方覆盖 | **100% 覆盖有/无 ERP 的买方企业** |
| 资金准确 | **对账周期内部分付款精确抵扣，账款分毫不差** |

### 1.3 核心价值主张

```
卖家 ERP 发起 → 自动拉取数据 → 关联期中付款 → 模板化生成对账单 → 自动推送买家
→ 买家多模式审核(ERP比对/平台手工/Excel上传/移动端) → 无异议电子签章 → 有异议在线协商
→ 签章完成 → 智能催收评分+分级催收 → 发票关联 → 保理融资(可选) → 款项到账闭环
```

### 3.2 万人在线高并发设计方案

#### 3.2.1 并发能力估算

```
目标: 10,000 人同时在线对账

峰值场景假设 (月末集中对账):
├── 同时在线用户:       10,000 人
├── 平均每人每分钟请求:   5 次 (浏览+操作)
├── 峰值请求量(QPS):     10,000 × 5 / 60 ≈ 834 QPS
├── 瞬时峰值 (3倍冗余):   ~2,500 QPS
├── 并发 PDF 生成:       高峰期约 200 任务/分钟
├── 并发比对任务:         高峰期约 100 任务/分钟
└── WebSocket 长连接:    10,000 条
```

#### 3.2.2 分层优化策略

**① 接入层**

| 策略 | 方案 | 说明 |
|------|------|------|
| 负载均衡 | Nginx + 云 SLB | 四层(TCP)+七层(HTTP) 双重负载均衡 |
| 静态加速 | CDN | 前端资源、PDF 文件通过 CDN 分发 |
| 连接复用 | HTTP/2 + Keep-Alive | 减少连接建立开销 |
| WebSocket | 独立 WS 网关 | 消息推送、实时通知使用长连接，与 HTTP 请求分离 |
| 限流保护 | Sentinel | API 级别限流，防止突发流量击穿 |

**② 应用层**

| 策略 | 方案 | 说明 |
|------|------|------|
| 服务实例 | 关键服务 ×3 实例 | recon-core 等核心服务至少 3 副本 |
| 弹性伸缩 | K8s HPA | 基于 CPU/QPS 自动扩缩容 |
| 异步解耦 | RabbitMQ | PDF 生成、比对任务、通知发送全部异步化 |
| 线程隔离 | 线程池隔离 | CPU 密集(比对)和 IO 密集(ERP拉取)使用不同线程池 |
| 熔断降级 | Sentinel | ERP 拉取超时自动熔断，不影响核心流程 |
| 无状态设计 | Session → Redis | 所有服务无状态，支持水平扩展 |

**③ 数据层**

| 策略 | 方案 | 说明 |
|------|------|------|
| 读写分离 | MySQL 一主多从 | 写操作走主库，列表查询走从库 |
| 分库策略 | 按企业 ID 分库 | 对账单按 seller_id 分库，避免单库瓶颈 |
| 分表策略 | 按月份分表 | recon_bill_item 按月分表，单表不超过 500 万行 |
| 多级缓存 | 本地 Caffeine + Redis | 模板配置/企业信息用本地缓存，热点数据 Redis 缓存 |
| 查询优化 | ES 搜索 + DB 详情 | 列表页走 ES，详情页走 DB |
| 连接池 | HikariCP | 单服务 50 连接，集群总连接数可控 |

**④ 异步任务架构**

```
┌────────────────────────────────────────────────────────────────┐
│                   异步任务处理架构                               │
│                                                                │
│  用户请求 ──→ API 接口 ──→ 创建任务记录(DB)                      │
│                    │                                           │
│                    ├──→ 发送MQ消息 ──→ 消费者处理               │
│                    │                    ├── PDF生成Worker(×4)   │
│                    │                    ├── 比对引擎Worker(×4)   │
│                    │                    ├── 通知发送Worker(×4)   │
│                    │                    ├── ERP拉取Worker(×4)   │
│                    │                    └── 催收执行Worker(×2)   │
│                    │                                           │
│                    └──→ 返回任务ID ──→ 前端轮询/WS推送进度       │

│  消费失败 ──→ 死信队列 ──→ 重试(3次) ──→ 人工介入                │

```

**⑤ 前端性能优化**

| 策略 | 说明 |
|------|------|
| 虚拟滚动 | 对账明细列表使用 vue-virtual-scroller，支持万条明细流畅滚动 |
| 懒加载 | 路由级别 Code Splitting，按模块按需加载 |
| 请求合并 | 列表页批量查询状态/统计，减少请求次数 |
| 离线缓存 | Service Worker 缓存静态资源 + IndexedDB 缓存草稿 |
| 分页加载 | 所有列表默认分页，每页 20 条，支持滚动加载 |
| 防抖节流 | 搜索输入 300ms 防抖，按钮操作 1s 节流 |
| WebSocket | 实时推送对账单状态变更，减少轮询 |

## 四、买方无 ERP 场景 — 多模式数据提交方案

### 4.1 问题分析

在钢铁行业，大量中小型买方企业并未使用 ERP 系统（或使用简单的进销存软件），这意味着：
- 无法通过 API 自动拉取买方数据进行比对
- 买方习惯使用 Excel 或手工台账管理采购记录
- 部分小微企业甚至只有纸质单据

### 4.2 多模式适配架构

```
┌─────────────────────────────────────────────────────────────────┐
│                  买方数据提交模式选择                              │
│                                                                 │

│  └────────────────┘                                             │

│  ┌─────────────────────────────────────────────────────────────┐│
│  │  模式A: ERP 自动比对 (有完整ERP的企业)                        ││
│  │  ├── API 对接拉取买方数据                                    ││
│  │  ├── 全自动比对，零人工干预                                   ││
│  │  └── 适合: 大中型企业、规范化管理的贸易商                      ││
│  ├─────────────────────────────────────────────────────────────┤│

│  │  ├── 买方下载标准模板 → 填写数据 → 上传平台                    ││
│  │  ├── 系统自动解析 → 智能字段映射 → 自动比对                    ││

│  ├─────────────────────────────────────────────────────────────┤│
│  │  模式C: 平台在线填写 (无电子数据的企业)                        ││
│  │  ├── 买方在平台上逐行核对卖方数据                              ││
```

## 五、对账周期内部分付款处理机制

### 5.1 问题场景

```
对账周期: 2026年2月1日 ~ 2026年2月28日

时间线:
  2/3   卖方发货 A批次 → 10万元
  2/8   买方付款 5万元 (部分付款 ①)
  2/10  卖方发货 B批次 → 15万元
  2/18  买方付款 8万元 (部分付款 ②)
  2/25  卖方发货 C批次 → 20万元
  2/28  对账周期结束

问题:
  - 周期内总交易额: 45万
  - 周期内已付款: 13万
  - 本期应付余额: 32万
  - 上期结转应付: 5万
  - 累计应付: 37万

  如何在对账单中准确反映这些信息？
  付款 ① 和 ② 分别抵扣哪些交易？
```

### 5.2 付款抵扣策略

系统支持三种付款抵扣策略，企业可自行选择：

```
┌─────────────────────────────────────────────────────────────────┐
│                    付款抵扣策略                                   │
│                                                                 │
│  策略一: 先进先出 (FIFO) ← 默认                                  │
│  ├── 按交易发生时间顺序抵扣                                       │
│  ├── 先付的款抵扣最早的应付                                       │
│  └── 示例: 2/8 付的5万 → 先抵扣 2/3 的A批次(10万中的5万)          │
│                                                                 │
│  策略二: 指定抵扣                                                 │
│  ├── 付款时指定抵扣的交易单据                                     │
│  ├── 一笔付款可拆分抵扣多笔交易                                   │
│  └── 示例: 2/8 付的5万 → 买方指定抵扣 A批次3万 + B批次2万          │
│                                                                 │
│  策略三: 按比例抵扣                                               │
│  ├── 按各笔交易金额占比均摊抵扣                                   │
│  ├── 适用于无法明确对应的预付款场景                                │
│  └── 示例: 付5万 → A占40%, B占60% → A抵2万, B抵3万               │
└─────────────────────────────────────────────────────────────────┘
```

### 7.4 自动比对规则设计 (v2.0 增强)

#### 比对维度

| 比对维度 | 匹配规则 | 容差设定 |
|---------|---------|---------|
| **单据匹配** | 按合同号/订单号精确匹配 | — |
| **品名规格** | 标准化后精确匹配 + 别名映射 | 支持配置别名表 |
| **数量** | 数值比对 | 允许设置容差（如 ±0.5%） |
| **重量** | 数值比对 + **重量差异归因** | 容差 ±0.3% + 自动分析差异原因 |
| **单价** | 数值比对 | 允许设置容差（如 ±1 元） |
| **金额** | 数值比对 | 允许设置容差（如 ±10 元） |
| **日期** | 日期比对 | 允许设置天数容差（如 ±3 天） |
| **付款** | 付款记录比对 | 金额容差 + 日期容差 |

#### 比对结果分类

```
比对结果
  ├── 完全匹配        ← 所有维度均在容差范围内
  ├── 部分匹配        ← 关键字段匹配，非关键字段有差异
  ├── 卖方多出        ← 卖方有此明细，买方无对应记录
  ├── 买方多出        ← 买方有此明细，卖方无对应记录
  ├── 金额差异        ← 匹配到记录但金额超出容差
  ├── 重量差异(已归因) ← 重量差异已自动分析原因
  └── 付款差异        ← 付款记录不一致
```

### 8.1 智能催收评分

**目标**: 基于买方历史行为数据，自动评估信用风险，驱动差异化催收策略。

**评分模型**:

```
信用评分 = Σ (因子得分 × 权重)

┌──────────────────────────────────────────────────────────────┐
│  因子              │ 权重 │ 计算方式                          │
│───────────────────┼──────┼───────────────────────────────────│
│  付款准时率        │ 30%  │ (准时付款次数/总付款次数)×100      │
│  平均付款天数      │ 20%  │ 与行业均值比较，越低越好            │
│  逾期金额占比      │ 20%  │ (逾期金额/总交易金额)×100, 取反    │
│  异议发生率        │ 10%  │ (异议次数/对账次数)×100, 取反      │
│  合作时长         │ 10%  │ 月数/基准月数, 上限100             │
│  交易规模         │ 10%  │ 交易额/基准额, 上限100             │
└──────────────────────────────────────────────────────────────┘

更新频率: 实时触发(回款/逾期事件) + 每日批量刷新
```

**功能要点**:
- 评分变化趋势可视化（折线图）
- 评级变更自动通知卖方管理员
- 评分低于阈值自动触发交易风控预警
- 支持人工调整评分（需审批+记录原因）

### 8.2 异议预测

**目标**: 在对账单生成时，预测每条明细引起异议的概率，提前预警。

**预测模型**:

```
输入特征:
├── 交易特征
│   ├── 品规复杂度(是否包含特殊规格)
│   ├── 交易金额大小
│   ├── 单价波动幅度(与近3个月均价偏差)
│   ├── 数量/重量差异历史分布
│   └── 是否涉及退货/补货
│
├── 客户特征
│   ├── 该客户历史异议率
│   ├── 该客户常见异议类型
│   └── 信用评分
│
├── 时间特征
│   ├── 月末/月初(财务结算期)
│   └── 距上次对账间隔天数
│
└── 匹配特征
    ├── 发货单与收货单时间差
    ├── 过磅重量与理论重量偏差
    └── 是否存在调价

输出:
├── 异议概率: 0~100 分
├── 风险等级: 低/中/高
└── 预测原因: "该客户历史上对Φ10盘螺的重量异议率达35%"

模型训练: 基于历史异议数据，使用梯度提升树(XGBoost/LightGBM)
```

### 8.3 自动容差学习

**目标**: 系统根据历史比对结果，自动优化每对买卖关系的容差参数。

**算法设计**:

```
┌──────────────────────────────────────────────────────────────┐
│                    自动容差学习引擎                            │
│                                                              │
│  数据收集:                                                    │
│  ├── 历史比对记录(最近 6 个月)                                 │
│  ├── 人工确认的"合理差异"记录                                  │
│  └── 异议中最终判定为"合理差异"的记录                           │
│                                                              │
│  分析维度: 按 (卖方, 买方, 品规, 维度) 四元组分析                │
│                                                              │
│  算法:                                                        │
│  ├── 1. 收集该四元组下所有比对的差异值                          │
│  ├── 2. 计算差异值的分布(均值、标准差、P95、P99)               │
│  ├── 3. 建议容差 = P95 值 (即覆盖95%的合理差异)               │
│  ├── 4. 计算采用建议容差后的:                                  │
│  │       - 匹配率变化 (应提升)                                │
│  │       - 误判率 (应 < 5%)                                  │
│  │       - 遗漏率 (真正的差异被忽略，应 < 1%)                  │
│  └── 5. 生成建议报告，等待管理员确认                           │
│                                                              │
│  安全机制:                                                    │
│  ├── 容差只建议放宽，不自动缩小                                │
```

### 8.4 重量差异归因

**目标**: 针对钢铁行业最常见的重量差异，自动分析差异原因，加速异议处理。

**归因分析模型**:

```
重量差异归因引擎
     │
     ├── 数据输入
     │   ├── 卖方过磅重量
     │   ├── 买方过磅重量
     │   ├── 理论重量(按国标计算)
     │   ├── 品名/规格/材质
     │   ├── 运输方式/距离
     │   ├── 天气情况(可选)
     │   └── 历史差异数据
     │
     ├── 归因规则库
     │   ├── R1: 磅差 (|差异| ≤ 0.3% 且无系统性偏差)
     │   │   → 原因: "正常过磅误差，在允许范围内"
     │   │
     │   ├── R2: 系统性偏差 (连续N次同方向偏差)
     │   │   → 原因: "疑似磅秤校准差异，建议双方校准磅秤"
     │   │
     │   ├── R3: 运输损耗 (差异与运输距离正相关)
     │   │   → 原因: "运输途中正常损耗，估算损耗率X%"
     │   │
     │   ├── R4: 含水量差异 (雨季差异增大)
     │   │   → 原因: "天气因素导致含水量差异"
     │   │
     │   ├── R5: 理论重量偏差 (与国标理重对比)
     │   │   → 原因: "实际重量与理论重量偏差属正常公差范围"
     │   │
     │   ├── R6: 数量差异 (差异刚好约等于整件重量)
     │   │   → 原因: "疑似漏发/漏收 N 件"
     │   │
     │   └── R7: 异常差异 (超出所有规则范围)
     │       → 原因: "差异异常，需人工核查"
     │
     └── 输出
         ├── 归因类别
         ├── 原因说明(自然语言)
         ├── 置信度
         └── 建议处理方式
```

## 十三、数据安全与合规设计

### 13.1 数据安全

| 维度 | 措施 |
|------|------|
| **传输安全** | 全链路 HTTPS/TLS 1.3 加密 |
| **存储安全** | 敏感字段 AES-256 加密存储（金额、账号等） |
| **访问控制** | RBAC 权限模型 + 数据行级隔离（企业维度） |
| **API 安全** | JWT Token + 接口签名 + Sentinel 限流 |
| **ERP 连接安全** | 连接凭证加密存储、最小权限原则 |
| **移动端安全** | 设备指纹 + Token 有效期缩短 + 敏感操作二次验证 |
| **审计追溯** | 全操作审计日志，保留期限 ≥ 3 年 |
| **融资安全** | 保理材料传输加密 + 数据脱敏 |

## 十六、风险与应对 (v2.0)

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| ERP 系统接口多样 | 集成周期延长 | Phase 1 先支持 REST + Excel 导入；逐步增加适配器 |
| 比对规则复杂 | 比对准确率低 | 别名映射表 + 模糊匹配 + 容差自动学习 + 人工兜底 |
| 签章法律效力认知不足 | 客户接受度低 | 选用权威签章服务，提供法律效力说明 |
| 买方无 ERP 使用门槛 | 买方不配合 | 提供5种模式适配，最简仅需"查看+确认"两步 |
| 付款抵扣逻辑复杂 | 数据不准确 | 默认 FIFO 策略 + 人工校正入口 + 双方确认 |
| 万人并发性能挑战 | 系统卡顿 | 分阶段压测、异步架构、弹性伸缩 |
| ML 模型冷启动 | 预测不准 | 初期使用规则引擎兜底，积累数据后切换 ML |
| 保理融资合规风险 | 法律纠纷 | 与合规律师合作，确保签章效力 |
| 超时自动确认争议 | 买方投诉 | 充分提前告知 + 事后申诉通道 |
| 移动端安全风险 | 信息泄露 | 设备指纹 + 操作水印 + 敏感操作二次验证 |

| 术语 | 英文 | 说明 |

| 对账单 | Reconciliation Bill | 卖方与买方对某一期间交易数据的核对单据 |

| 账期 | Payment Term | 约定的付款期限 |

| 保理 | Factoring | 应收账款转让融资 |
