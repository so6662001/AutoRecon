## 一、项目背景与目标

### 1.1 业务背景

钢铁行业交易具有**大宗、高频、多品规、多批次**的特点，买卖双方在一个结算周期内可能产生数十甚至数百笔交易。传统对账依赖线下 Excel 传递、人工核对，存在以下痛点：

| 痛点 | 影响 |
|------|------|
| 对账周期长 | 平均 5-10 个工作日完成一轮对账 |
| 差异排查难 | 多品规/多批次场景下人工比对效率极低 |
| 沟通成本高 | 电话、微信、邮件多渠道反复沟通 |
| 确认无凭证 | 双方确认结果缺乏法律效力 |
| 催收脱节 | 对账完成后催款依赖人工跟进，容易遗漏 |
| 买方能力参差 | 部分买方无 ERP 系统，只能手工管理，对账全靠 Excel/纸质 |
| 期中付款混乱 | 对账周期内买方已支付部分款项，但对账时难以准确抵扣 |

### 1.2 项目目标

构建一套 **"ERP 驱动 + 多模式适配、模板化生成、自动化比对、电子签章确认、智能催收闭环"** 的线上对账系统：

| 目标 | 指标 |
|------|------|
| 对账效率 | 对账周期从 5-10 天缩短至 1-2 天 |
| 异议处理 | 异议处理效率提升 60% 以上 |
| 并发能力 | **支持 10,000 人同时在线对账** |
| 买方覆盖 | **100% 覆盖有/无 ERP 的买方企业** |
| 资金准确 | **对账周期内部分付款精确抵扣，账款分毫不差** |

### 1.3 核心价值主张

```
卖家 ERP 发起 → 自动拉取数据 → 关联期中付款 → 模板化生成对账单 → 自动推送买家
→ 买家多模式审核(ERP比对/平台手工/Excel上传/移动端) → 无异议电子签章 → 有异议在线协商
→ 签章完成 → 智能催收评分+分级催收 → 发票关联 → 保理融资(可选) → 款项到账闭环
```

### 3.2 万人在线高并发设计方案

#### 3.2.1 并发能力估算

```
目标: 10,000 人同时在线对账

峰值场景假设 (月末集中对账):
├── 同时在线用户:       10,000 人
├── 平均每人每分钟请求:   5 次 (浏览+操作)
├── 峰值请求量(QPS):     10,000 × 5 / 60 ≈ 834 QPS
├── 瞬时峰值 (3倍冗余):   ~2,500 QPS
├── 并发 PDF 生成:       高峰期约 200 任务/分钟
├── 并发比对任务:         高峰期约 100 任务/分钟
└── WebSocket 长连接:    10,000 条
```

#### 3.2.2 分层优化策略

**① 接入层**

| 策略 | 方案 | 说明 |
|------|------|------|
| 负载均衡 | Nginx + 云 SLB | 四层(TCP)+七层(HTTP) 双重负载均衡 |
| 静态加速 | CDN | 前端资源、PDF 文件通过 CDN 分发 |
| 连接复用 | HTTP/2 + Keep-Alive | 减少连接建立开销 |
| WebSocket | 独立 WS 网关 | 消息推送、实时通知使用长连接，与 HTTP 请求分离 |
| 限流保护 | Sentinel | API 级别限流，防止突发流量击穿 |

**② 应用层**

| 策略 | 方案 | 说明 |
|------|------|------|
| 服务实例 | 关键服务 ×3 实例 | recon-core 等核心服务至少 3 副本 |
| 弹性伸缩 | K8s HPA | 基于 CPU/QPS 自动扩缩容 |
| 异步解耦 | RabbitMQ | PDF 生成、比对任务、通知发送全部异步化 |
| 线程隔离 | 线程池隔离 | CPU 密集(比对)和 IO 密集(ERP拉取)使用不同线程池 |
| 熔断降级 | Sentinel | ERP 拉取超时自动熔断，不影响核心流程 |
| 无状态设计 | Session → Redis | 所有服务无状态，支持水平扩展 |

**③ 数据层**

| 策略 | 方案 | 说明 |
|------|------|------|
| 读写分离 | MySQL 一主多从 | 写操作走主库，列表查询走从库 |
| 分库策略 | 按企业 ID 分库 | 对账单按 seller_id 分库，避免单库瓶颈 |
| 分表策略 | 按月份分表 | recon_bill_item 按月分表，单表不超过 500 万行 |
| 多级缓存 | 本地 Caffeine + Redis | 模板配置/企业信息用本地缓存，热点数据 Redis 缓存 |
| 查询优化 | ES 搜索 + DB 详情 | 列表页走 ES，详情页走 DB |
| 连接池 | HikariCP | 单服务 50 连接，集群总连接数可控 |

**④ 异步任务架构**

```
┌────────────────────────────────────────────────────────────────┐
│                   异步任务处理架构                               │
│                                                                │
│  用户请求 ──→ API 接口 ──→ 创建任务记录(DB)                      │
│                    │                                           │
│                    ├──→ 发送MQ消息 ──→ 消费者处理               │
│                    │                    ├── PDF生成Worker(×4)   │
│                    │                    ├── 比对引擎Worker(×4)   │
│                    │                    ├── 通知发送Worker(×4)   │
│                    │                    ├── ERP拉取Worker(×4)   │
│                    │                    └── 催收执行Worker(×2)   │
│                    │                                           │
│                    └──→ 返回任务ID ──→ 前端轮询/WS推送进度       │

│  消费失败 ──→ 死信队列 ──→ 重试(3次) ──→ 人工介入                │

```

**⑤ 前端性能优化**

| 策略 | 说明 |
|------|------|
| 虚拟滚动 | 对账明细列表使用 vue-virtual-scroller，支持万条明细流畅滚动 |
| 懒加载 | 路由级别 Code Splitting，按模块按需加载 |
| 请求合并 | 列表页批量查询状态/统计，减少请求次数 |
| 离线缓存 | Service Worker 缓存静态资源 + IndexedDB 缓存草稿 |
| 分页加载 | 所有列表默认分页，每页 20 条，支持滚动加载 |
| 防抖节流 | 搜索输入 300ms 防抖，按钮操作 1s 节流 |
| WebSocket | 实时推送对账单状态变更，减少轮询 |

## 四、买方无 ERP 场景 — 多模式数据提交方案

### 4.1 问题分析

在钢铁行业，大量中小型买方企业并未使用 ERP 系统（或使用简单的进销存软件），这意味着：
- 无法通过 API 自动拉取买方数据进行比对
- 买方习惯使用 Excel 或手工台账管理采购记录
- 部分小微企业甚至只有纸质单据

### 4.2 多模式适配架构

```
┌─────────────────────────────────────────────────────────────────┐
│                  买方数据提交模式选择                              │
│                                                                 │

│  └────────────────┘                                             │

│  ┌─────────────────────────────────────────────────────────────┐│
│  │  模式A: ERP 自动比对 (有完整ERP的企业)                        ││
│  │  ├── API 对接拉取买方数据                                    ││
│  │  ├── 全自动比对，零人工干预                                   ││
│  │  └── 适合: 大中型企业、规范化管理的贸易商                      ││
│  ├─────────────────────────────────────────────────────────────┤│

│  │  ├── 买方下载标准模板 → 填写数据 → 上传平台                    ││
│  │  ├── 系统自动解析 → 智能字段映射 → 自动比对                    ││

│  ├─────────────────────────────────────────────────────────────┤│
│  │  模式C: 平台在线填写 (无电子数据的企业)                        ││
│  │  ├── 买方在平台上逐行核对卖方数据                              ││
```

## 五、对账周期内部分付款处理机制

### 5.1 问题场景

```
对账周期: 2026年2月1日 ~ 2026年2月28日

时间线:
  2/3   卖方发货 A批次 → 10万元
  2/8   买方付款 5万元 (部分付款 ①)
  2/10  卖方发货 B批次 → 15万元
  2/18  买方付款 8万元 (部分付款 ②)
  2/25  卖方发货 C批次 → 20万元
  2/28  对账周期结束

问题:
  - 周期内总交易额: 45万
  - 周期内已付款: 13万
  - 本期应付余额: 32万
  - 上期结转应付: 5万
  - 累计应付: 37万

  如何在对账单中准确反映这些信息？
  付款 ① 和 ② 分别抵扣哪些交易？
```

### 5.2 付款抵扣策略

系统支持三种付款抵扣策略，企业可自行选择：

```
┌─────────────────────────────────────────────────────────────────┐
│                    付款抵扣策略                                   │
│                                                                 │
│  策略一: 先进先出 (FIFO) ← 默认                                  │
│  ├── 按交易发生时间顺序抵扣                                       │
│  ├── 先付的款抵扣最早的应付                                       │
│  └── 示例: 2/8 付的5万 → 先抵扣 2/3 的A批次(10万中的5万)          │
│                                                                 │
│  策略二: 指定抵扣                                                 │
│  ├── 付款时指定抵扣的交易单据                                     │
│  ├── 一笔付款可拆分抵扣多笔交易                                   │
│  └── 示例: 2/8 付的5万 → 买方指定抵扣 A批次3万 + B批次2万          │
│                                                                 │
│  策略三: 按比例抵扣                                               │
│  ├── 按各笔交易金额占比均摊抵扣                                   │
│  ├── 适用于无法明确对应的预付款场景                                │
│  └── 示例: 付5万 → A占40%, B占60% → A抵2万, B抵3万               │
└─────────────────────────────────────────────────────────────────┘
```

**合同号设计说明:**

钢铁行业交易存在**有合同**和**无合同(现货/零单)**两种模式，对账单明细需同时支持：

```
单据层级关系:

  有合同的交易:
  合同(contract_no) → 订单(order_no) → 发货单(delivery_no)
  │                   │                │
  │ 框架合同，约定     │ 具体批次下单     │ 实际发货记录
  │ 总量/价格/交货期   │ 品规/数量/交期   │ 实发数量/重量
  │                   │                │
  例: HT2026-0023     例: OD20260205001  例: FH20260208015

  无合同的交易(现货/零单):
  订单(order_no) → 发货单(delivery_no)
```

### 7.4 自动比对规则设计 (v2.0 增强)

#### 比对维度

| 比对维度 | 匹配规则 | 容差设定 |
|---------|---------|---------|
| **合同号** | 精确匹配（有合同的交易优先按合同号锁定范围） | — |
| **订单号** | 精确匹配（合同内按订单号细分） | — |
| **发货单号** | 精确匹配（最终按发货单号逐笔对应） | — |
| **品名规格** | 标准化后精确匹配 + 别名映射 | 支持配置别名表 |
| **数量** | 数值比对 | 允许设置容差（如 ±0.5%） |
| **重量** | 数值比对 + **重量差异归因** | 容差 ±0.3% + 自动分析差异原因 |
| **单价** | 数值比对 | 允许设置容差（如 ±1 元） |
| **金额** | 数值比对 | 允许设置容差（如 ±10 元） |
| **日期** | 日期比对 | 允许设置天数容差（如 ±3 天） |
| **付款** | 付款记录比对 | 金额容差 + 日期容差 |

#### 单据匹配优先级策略

```
比对引擎按以下优先级链逐级匹配:

优先级1: 发货单号精确匹配 (最精确)
  卖方 delivery_no = 买方 delivery_no
  → 匹配到 → 直接比对数量/重量/金额

优先级2: 订单号 + 品规匹配
  卖方 (order_no, product_name, spec) = 买方同组合
  → 匹配到 → 比对数量/重量/金额

优先级3: 合同号 + 品规 + 日期范围匹配
  卖方 (contract_no, product_name, spec) = 买方同组合
  且发货日期在 ±N 天容差内
  → 匹配到 → 比对数量/重量/金额

优先级4: 品规 + 金额 模糊匹配 (无合同/无单号的零单)
  品名规格匹配 + 金额在容差范围内 + 日期在容差内
  → 候选匹配 → 标记为"模糊匹配，建议人工确认"

合同维度校验 (有合同的交易额外检查):
  同一合同下所有明细匹配完成后，校验:
  ├── 合同总量 vs 实际发货总量
  ├── 合同总金额 vs 实际结算总金额
  └── 差异超阈值 → 标记合同级预警
```

#### 比对结果分类

```
比对结果
  ├── 完全匹配        ← 所有维度均在容差范围内
  ├── 部分匹配        ← 关键字段匹配，非关键字段有差异
  ├── 卖方多出        ← 卖方有此明细，买方无对应记录
  ├── 买方多出        ← 买方有此明细，卖方无对应记录
  ├── 金额差异        ← 匹配到记录但金额超出容差
  ├── 重量差异(已归因) ← 重量差异已自动分析原因
  └── 付款差异        ← 付款记录不一致
```

#### 7.6.5 签章安全与合规设计

```
┌──────────────────────────────────────────────────────────────────┐
│                   签章安全与合规                                   │
│                                                                  │
│  身份验证安全:                                                    │
│  ├── 短信验证码: 6位数字，5分钟有效，同一手机号每日上限10次        │
│  ├── 人脸识别: 活体检测(眨眼/点头/张嘴)，防照片/视频攻击           │

│  ├── 印章图片不落地: 印章图片存储在第三方签章平台，平台只存印章ID   │
│  ├── 签章操作防重放: 每次签章请求携带唯一nonce+时间戳+签名          │
│  ├── 操作水印: H5/PC端签章页面添加用户信息水印，防截图泄露          │

│                                                                  │

│  ├── 法律依据: 《电子签名法》《民法典》电子合同相关条款             │
│  ├── 企业实名认证: 对接工商数据源核验，确保企业真实存在             │
```

### 8.1 智能催收评分

**目标**: 基于买方历史行为数据，自动评估信用风险，驱动差异化催收策略。

**评分模型**:

```
信用评分 = Σ (因子得分 × 权重)

┌──────────────────────────────────────────────────────────────┐
│  因子              │ 权重 │ 计算方式                          │
│───────────────────┼──────┼───────────────────────────────────│
│  付款准时率        │ 30%  │ (准时付款次数/总付款次数)×100      │
│  平均付款天数      │ 20%  │ 与行业均值比较，越低越好            │
│  逾期金额占比      │ 20%  │ (逾期金额/总交易金额)×100, 取反    │
│  异议发生率        │ 10%  │ (异议次数/对账次数)×100, 取反      │
│  合作时长         │ 10%  │ 月数/基准月数, 上限100             │
│  交易规模         │ 10%  │ 交易额/基准额, 上限100             │
└──────────────────────────────────────────────────────────────┘

更新频率: 实时触发(回款/逾期事件) + 每日批量刷新
```

**功能要点**:
- 评分变化趋势可视化（折线图）
- 评级变更自动通知卖方管理员
- 评分低于阈值自动触发交易风控预警
- 支持人工调整评分（需审批+记录原因）

### 8.2 异议预测

**目标**: 在对账单生成时，预测每条明细引起异议的概率，提前预警。

**预测模型**:

```
│   ├── 数量/重量差异历史分布
│   └── 是否涉及退货/补货

├── 客户特征
│   ├── 该客户历史异议率
│   ├── 该客户常见异议类型
│   └── 信用评分

├── 时间特征

└── 匹配特征

├── 风险等级: 低/中/高
```

### 8.3 自动容差学习

**目标**: 系统根据历史比对结果，自动优化每对买卖关系的容差参数。

**算法设计**:

```
┌──────────────────────────────────────────────────────────────┐
│                    自动容差学习引擎                            │
│                                                              │
│  数据收集:                                                    │
│  ├── 历史比对记录(最近 6 个月)                                 │
│  ├── 人工确认的"合理差异"记录                                  │
│  └── 异议中最终判定为"合理差异"的记录                           │
│                                                              │
│  分析维度: 按 (卖方, 买方, 品规, 维度) 四元组分析                │
│                                                              │
│  算法:                                                        │
│  ├── 1. 收集该四元组下所有比对的差异值                          │
│  ├── 2. 计算差异值的分布(均值、标准差、P95、P99)               │
│  ├── 3. 建议容差 = P95 值 (即覆盖95%的合理差异)               │
│  ├── 4. 计算采用建议容差后的:                                  │
│  │       - 匹配率变化 (应提升)                                │
│  │       - 误判率 (应 < 5%)                                  │
│  │       - 遗漏率 (真正的差异被忽略，应 < 1%)                  │
│  └── 5. 生成建议报告，等待管理员确认                           │
│                                                              │
│  安全机制:                                                    │
│  ├── 容差只建议放宽，不自动缩小                                │
│  ├── 放宽幅度上限: 当前值的 200%                               │
│  ├── 必须管理员审批后生效                                      │
│  └── 生效后持续监控误判率，异常自动回退                         │
│                                                              │
│  执行频率: 每月 1 日自动分析，生成建议报告                      │
└──────────────────────────────────────────────────────────────┘
```

### 8.4 重量差异归因

**目标**: 针对钢铁行业最常见的重量差异，自动分析差异原因，加速异议处理。

**归因分析模型**:

```
重量差异归因引擎
     │
     ├── 数据输入
     │   ├── 卖方过磅重量
     │   ├── 买方过磅重量
     │   ├── 理论重量(按国标计算)
     │   ├── 品名/规格/材质
     │   ├── 运输方式/距离
     │   ├── 天气情况(可选)
     │   └── 历史差异数据
     │
     ├── 归因规则库
     │   ├── R1: 磅差 (|差异| ≤ 0.3% 且无系统性偏差)
     │   │   → 原因: "正常过磅误差，在允许范围内"
     │   │
     │   ├── R2: 系统性偏差 (连续N次同方向偏差)
     │   │   → 原因: "疑似磅秤校准差异，建议双方校准磅秤"
     │   │
     │   ├── R3: 运输损耗 (差异与运输距离正相关)
     │   │   → 原因: "运输途中正常损耗，估算损耗率X%"
     │   │
     │   ├── R4: 含水量差异 (雨季差异增大)
     │   │   → 原因: "天气因素导致含水量差异"
     │   │
     │   ├── R5: 理论重量偏差 (与国标理重对比)
     │   │   → 原因: "实际重量与理论重量偏差属正常公差范围"
     │   │
     │   ├── R6: 数量差异 (差异刚好约等于整件重量)
     │   │   → 原因: "疑似漏发/漏收 N 件"
     │   │
     │   └── R7: 异常差异 (超出所有规则范围)
     │       → 原因: "差异异常，需人工核查"
     │
     └── 输出
         ├── 归因类别
         ├── 原因说明(自然语言)
         ├── 置信度
         └── 建议处理方式
```

## 十六、买方信任构建与渐进式引导设计

### 16.1 问题分析

新买方拒绝使用平台的核心顾虑：

| 顾虑层次 | 具体表现 | 心理本质 |
|---------|---------|---------|
| **数据安全** | "我的采购数据放到你平台上安全吗？" | 对平台掌握己方商业数据的恐惧 |
| **法律效力** | "电子签章真的有法律效力吗？打官司认吗？" | 对新事物法律风险的不确定感 |
| **操作复杂** | "我们就几个人，哪有精力学一个新系统？" | 对使用成本的预估 |
| **被锁定** | "上了你的平台以后是不是就离不开了？" | 对供应商依赖的防御心理 |
| **费用** | "这个对我有什么好处？还要收费？" | 买方作为被动方缺乏动力 |
| **信任传递** | "我跟卖方关系好得很，何必多此一举？" | 对已有合作模式的路径依赖 |
| **隐私** | "你们能看到我跟所有卖方的交易？" | 担心平台利用交易数据 |

### 16.8 免注册对账确认的法律效力保障

```
免注册模式下买方"确认无异议"的法律效力链:

1. 身份确认: 买方通过手机验证码验证身份
   → 手机号与卖方在平台登记的买方联系人手机号一致
   → 相当于"以约定的方式确认"

2. 操作记录: 系统完整记录
   → 操作时间、IP地址、设备信息、手机验证码验证记录
   → 形成完整的电子证据链

3. 通知送达: 系统记录
   → 短信发送记录(运营商回执)
   → 链接打开记录(时间+IP)
   → 形成"已有效送达"的证据

4. 法律说明:
   → 免注册确认视为"以行为方式表示同意"
   → 效力等级低于电子签章，但高于口头/微信确认
   → 适用于金额较小或双方信任度较高的场景
   → 对账单 PDF 中标注"本对账单通过平台在线确认(非签章)"

5. 升级提示:
   → 确认完成后提示"如需更高法律效力，建议升级至电子签章"
   → 高金额对账单(>50万)自动提示"建议使用电子签章确认"
```

#### 卖方 ROI 测算

```
以"中型钢贸商"为例:

投入:
  年费: ¥2,999 × 12 = ¥35,988 (年付优惠后 ¥29,999)
  签章: ¥3/次 × 200次 × 12月 = ¥7,200
  年度总投入: ≈ ¥37,199

产出:
  ① 人力节省
     原对账人员: 2人 × ¥8,000/月 × 50%时间用于对账 = ¥8,000/月
     使用平台后: 1人 × ¥8,000/月 × 20%时间 = ¥1,600/月
     月节省: ¥6,400  年节省: ¥76,800

  ② 回款加速
     月均应收: ¥5,000,000
     原平均回款天数: 45天 → 使用后: 35天  缩短10天
     资金成本节省: ¥5,000,000 × 5%年利率 × 10/365 = ¥6,849/月
     年节省: ¥82,192

  ③ 坏账减少
     年均坏账率从 1.5% 降至 0.8%
     年交易额 ¥60,000,000 × 0.7% = ¥420,000

  年度总产出: ¥76,800 + ¥82,192 + ¥420,000 = ¥578,992

  ROI = (¥578,992 - ¥37,199) / ¥37,199 = 1,456%
```

### 17.12 收费机制风险与应对

| 风险 | 应对 |
|------|------|
| 卖方觉得贵，不愿付费 | 提供免费版长期使用 + 30天标准版试用 + ROI计算器帮助卖方算清投入产出 |
| 签章按次收费导致卖方不愿签章 | 签章包阶梯价格，量越大越便宜；高套餐可含签章额度 |
| 买方不理解"为什么免费" | 在平台多处展示"买方永久免费"标识，消除疑虑 |
| 月末集中对账导致超限 | 宽限机制 + 超出按量计费，不硬性拦截 |
| 竞品打价格战 | 差异化竞争（钢铁行业深度适配、重量差异归因等行业独有功能），而非纯比价格 |
| 客户降级后数据处理 | 数据保留 90 天，期间可随时升级恢复；超期数据归档而非删除 |
