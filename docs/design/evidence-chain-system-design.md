## 一、项目背景与目标

### 1.1 业务背景

钢铁行业赊销交易中，卖方最大的风险是**"货发了，钱收不回来，还没证据"**。传统业务流程中，合同签署、派车提货、仓库发货、结算确认等环节分散在多个系统和纸质单据中，一旦发生欠款纠纷，卖方往往面临：

| 痛点 | 影响 |
|------|------|
| 合同仅在 ERP 中，客户未签字 | 合同真实性易被质疑 |
| 提货过程无完整记录 | 无法证明"谁提了多少货" |
| 发货仅有仓库内部记录 | 买方可否认收到货物 |
| 过磅/吊装数据散落 | 重量争议无法追溯 |
| 结算单未经客户确认 | 应收金额缺乏双方共识 |
| 各环节数据不打通 | 无法形成完整"合同→提货→发货→结算"证据链 |

### 1.2 项目目标

构建一套 **"合同在线签约 → 智能派车 → 电子提货单 → 多模式发货采集(WMS/H5/驾驶员/第三方) → 结算自动生成 → 欠款证据闭环"** 的证据链系统：

| 目标 | 指标 |
|------|------|
| 证据完整度 | 每笔交易100%覆盖合同→提货→发货→结算全链路 |
| 客户实时感知 | 合同签约/派车/提货/发货/结算 每个节点实时推送 |
| 法律效力 | 关键节点电子签章+全链路存证，具备诉讼证据效力 |
| 多端覆盖 | PC(Vue3) + H5移动端(客户+仓库H5助手) + 微信小程序(驾驶员) + Android WMS(可选) |
| 仓库适配 | **100% 覆盖有 WMS 和无 WMS 的仓库，5 种发货模式适配** |
| 系统集成 | 与 ERP(合同源)、WMS(自有/第三方)、对账系统(AutoRecon) 无缝对接 |

### 1.3 核心价值主张

```
ERP合同生效 → 推送客户在线签约 → 客户/销售派车 → 生成电子提货单+提货码
→ 驾驶员小程序接单 → 到达仓库 → 多模式发货(WMS/H5助手/第三方WMS/驾驶员确认)
→ 逐吊采集(实时上传) → 发货完成签字+拍照 → 结算智能体生成结算单 → 推送客户确认
→ 全链路证据自动归档 → 欠款有据可查、有链可追
```

### 4.2 合同管理与签约（按合同类型差异化）

#### 4.2.1 核心设计原则：不改变客户习惯

```
┌──────────────────────────────────────────────────────────────────────┐
│                    关键业务洞察                                       │
│                                                                      │
│  留货合同的现实情况:                                                  │
│  ├── 客户已在 ERP 中与销售谈好价格、品规、数量                        │
│  ├── 货物已在仓库中锁定，客户随时可提                                │
│  ├── 客户提货方式: 打电话/发微信告诉司机"去XX仓库提我的货"             │
│  ├── 司机到了仓库直接报客户名字就提货                                │
│  └── 客户不愿意多做任何操作(签约/派车/确认)                           │
│                                                                      │
│  如果强制客户先签约再派车:                                            │
│  ├── 客户觉得麻烦 → 不来提货 → 转向竞争对手                          │
│  ├── 销售员夹在中间左右为难                                          │
│  └── 系统沦为摆设                                                    │
│                                                                      │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │                                                              │   │
│  │  设计原则: 让系统适应人，不是让人适应系统                       │   │
│  │                                                              │   │
│  │  留货合同 → "静默采集模式"                                    │   │
│  │    客户什么都不用做，系统自动在仓库发货环节采集证据              │   │
│  │    签约/确认改为"事后追认"，不阻塞提货流程                      │   │
│  │                                                              │   │
│  │  订货合同 → "主动流程模式"                                    │   │
│  │    合同需要双方确认条款(价格/交期/品规可能有变化)               │   │
│  │    签约是必要的商业行为，不是额外负担                           │   │
│  │                                                              │   │
│  └──────────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────────┘
```

#### 4.2.2 留货合同 — 静默采集模式

**核心思路**: 客户的操作流程完全不变（打电话→司机去提货），系统在仓库端"静默"采集证据，提货完成后再通知客户确认。

```
┌──────────────────────────────────────────────────────────────────────┐
│               留货合同 — 静默采集模式 (客户零操作)                     │
│                                                                      │
│  ┌─── 客户视角 (和以前一模一样) ─────────────────────────────────┐  │
│  │                                                                │  │
│  │  客户打电话/发微信给司机: "去XX仓库帮我拉100吨螺纹钢"           │  │
│  │       │                                                        │  │
│  │       ▼                                                        │  │
│  │  司机到仓库 → 报客户名/合同号 → 仓库发货 → 拉走                │  │
│  │       │                                                        │  │
│  │       ▼                                                        │  │
│  │  客户收到短信: "您在XX仓库提了98.3吨螺纹钢，点击查看详情"       │  │
│  │  (客户可以看，也可以不看，不影响任何流程)                        │  │
│  │                                                                │  │
│  │  客户感受: "跟以前一样，就是多收了条短信"                        │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  ┌─── 系统视角 (后台静默运行 + 提货确权) ──────────────────────┐  │
│  │                                                                │  │
│  │  ① ERP 合同生效 → 自动同步到证据链系统 (后台，无通知)           │  │
│  │     合同状态直接设为"可提货"(留货合同无需签约即可提)              │  │
│  │     │                                                          │  │
│  │     ▼                                                          │  │
│  │  ② 司机到仓库 → 仓库在系统中开始发货:                           │  │
│  │     ├── 仓库输入: 客户名称/合同号 (系统自动匹配合同)             │  │
│  │     ├── 或: 客户提前告诉销售合同号，销售在系统预录               │  │
│  │     ├── 或: 仓库扫描合同条码/留货标签                           │  │
│  │     └── 采集司机身份信息 (见下方 4.2.5 提货确权机制)            │  │
│  │     │                                                          │  │
│  │     ▼                                                          │  │
│  │  ②-B 提货确权 (自动触发，客户被动确认):                         │  │
│  │     ├── 系统自动发送确权短信/企微给客户(详见 4.2.5)              │  │
│  │     ├── 客户不需要回复也不阻塞发货                              │  │
│  │     ├── 但如果客户回复"否"→ 立即暂停发货 + 通知仓库              │  │
│  │     └── 同时系统自动创建提货单                                  │  │
│  │     │                                                          │  │
│  │     ▼                                                          │  │
│  │  ③ 仓库发货过程 → 正常采集证据 (WMS/H5助手/驾驶员确认)          │  │
│  │     ├── 逐吊记录 + 签字 + 拍照                                 │  │
│  │     ├── 记录司机信息(车牌/姓名/电话 — 仓库现场采集)             │  │
│  │     ├── 拍摄司机身份证/驾驶证照片                               │  │
│  │     └── 司机在发货单上签字(纸质或电子)                          │  │
│  │     │                                                          │  │
│  │     ▼                                                          │  │
│  │  ④ 发货完成 → 系统自动:                                        │  │
│  │     ├── 生成结算单                                             │  │
│  │     ├── 归档证据包                                             │  │
│  │     ├── 推送通知给客户 (事后通知，非事前确认)                    │  │
│  │     │   "您在XX仓库提货98.3吨，金额¥412,860，点击查看详情"      │  │
│  │     └── 推送通知给销售员                                       │  │
│  │     │                                                          │  │
│  │     ▼                                                          │  │
│  │  ⑤ 客户事后可选操作 (全部为可选，不强制):                       │  │
│  │     ├── 查看提货详情和结算单 → 增加客户知情度                   │  │
│  │     ├── 确认无异议 → 增强证据效力                               │  │
│  │     ├── 提出异议 → 进入异议处理流程                             │  │

│  │                                                                │  │
│  │  证据链即使客户不操作也完整:                                     │  │
│  │  ERP合同 + 仓库发货记录 + 逐吊明细 + 司机签字 +                 │  │
│  │  现场照片 + 结算单 + 客户通知记录(送达证明)                      │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  ┌─── 签约策略: 不阻塞，柔性引导 ───────────────────────────────┐  │
│  │                                                                │  │
│  │  留货合同签约不是提货的前置条件:                                 │  │
│  │  ├── 不签约也可以提货 (ERP合同+提货记录=充分证据)               │  │
│  │  ├── 签约作为"增强选项"，在合适时机柔性引导:                    │  │

│  │  │   └── 时机4: 累计提货金额达到阈值时建议签章                  │  │
│  │  │                                                             │  │
│  │  ├── 签约率作为运营指标跟踪，但不作为强制要求                   │  │
│  │  └── 即使0%签约率，证据链仍然有效(仓库采集+司机签字)            │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  └────────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
```

#### 4.2.3 提货确权机制（解决"客户否认派车"的法律难题）

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│             解决核心法律问题: "客户否认是他派车来提货"                  │
│                                                                      │
│  ┌─── 问题分析 ──────────────────────────────────────────────────┐  │
│  │                                                                │  │
│  │  败诉场景还原:                                                  │  │
│  │  ├── 卖方: "客户派司机来提了100吨钢材"                          │  │
│  │  ├── 客户: "我没有派任何人去提货，不认识这个司机"                │  │
│  │  ├── 法院: "你能证明这个司机是客户派来的吗？"                    │  │
│  │  ├── 卖方: "......" (只有仓库发货记录和司机签字)                │  │
│  │  └── 法院: "证据不足，无法认定客户授权提货，驳回"                │  │
│  │                                                                │  │
│  │  关键缺失: 缺少"客户"与"提货行为"之间的授权关联证据              │  │
│  │                                                                │  │
│  │  法院认可的授权证据:                                            │  │
│  │  ├── 书面授权委托书 (最强，但留货场景客户不会配合)               │  │
│  │  ├── 客户预先登记的提货人清单 (次强)                            │  │
│  │  ├── 客户在提货时的电话/短信确认 (有效)                         │  │
│  │  ├── 客户事后知情且未提异议的记录 (辅助)                        │  │
│  │  └── 交易习惯证据链 (历史多次同一模式提货+付款)                 │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  ┌─── 设计方案: 五层确权证据体系 ────────────────────────────────┐  │
│  │                                                                │  │
│  │  不依赖任何单一证据，五层叠加形成"不可否认"的证据链              │  │
│  │                                                                │  │
│  │                                                                │  │
│  │  ═══ 第一层: 提货人预登记 (长期有效，一次操作) ═══              │  │
│  │                                                                │  │
│  │  客户在系统中预先登记"授权提货人":                               │  │
│  │  ├── 登记信息: 提货人姓名 + 身份证号 + 手机号 + 车牌号          │  │
│  │  ├── 授权范围: 可提货的合同/可提的品规/最大单次提货量            │  │
│  │  ├── 有效期: 可设置长期有效或指定截止日期                       │  │
│  │  ├── 操作方式:                                                 │  │
│  │  │   ├── 客户在 H5 端自行登记 (最佳)                           │  │
│  │  │   ├── 销售员代为录入 → 推送客户确认(短信链接, 一键确认)      │  │
│  │  │   └── 首次提货时仓库现场采集 → 推送客户追认                  │  │
│  │  ├── 证据效力: 客户主动登记 = 书面授权等效                      │  │
│  │  │   销售代录+客户确认 = 有确认记录佐证                         │  │
│  │  │   仓库采集+客户追认 = 事后追认                               │  │
│  │  └── 引导策略:                                                 │  │
│  │      ├── 签合同时顺带录入: "顺便登记一下常用的提货司机"          │  │
│  │      ├── 首次提货后引导: "您刚才的司机下次还来吧？登记后更方便"  │  │
│  │      └── 不登记也能提货(不阻塞), 但系统标注"未预登记提货人"     │  │
│  │                                                                │  │
│  │                                                                │  │
│  │  ═══ 第二层: 提货时实时确权短信 (每次提货自动触发) ═══          │  │
│  │                                                                │  │
│  │  仓库开始发货时，系统自动发送确权短信给客户:                      │  │
│  │                                                                │  │
│  │  ┌──────────────────────────────────────────┐                  │  │
│  │  │ 【XX钢铁】您的提货人[王五](车牌沪A12345) │                  │  │
│  │  │ 正在XX仓库提货，合同号HT2026-0023，       │                  │  │
│  │  │ 品规:螺纹钢Φ20约100吨。                   │                  │  │
│  │  │ 如非本人安排，请立即回复N或致电XXX。       │                  │  │
│  │  │ [查看详情: https://xxx/v/xxx]              │                  │  │
│  │  └──────────────────────────────────────────┘                  │  │
│  │                                                                │  │
│  │  确权逻辑:                                                     │  │
│  │  ├── 短信发出 → 运营商返回送达回执 → 证明客户已收到通知         │  │
│  │  ├── 客户不回复 → 视为"默认认可"(合同条款中预先约定)            │  │
│  │  ├── 客户回复"N"或来电否认 → 立即暂停发货 + 通知仓库 + 报警     │  │
│  │  ├── 客户点击链接查看 → 记录查看时间/IP → 证明知情              │  │
│  │  └── 短信不阻塞发货流程(发完短信仓库继续装货)                   │  │
│  │                                                                │  │
│  │  证据效力:                                                     │  │
│  │  ├── 短信送达回执(运营商级别) = 客户已收到通知                  │  │
│  │  ├── 客户未否认 = 在合同约定框架下视为认可                      │  │
│  │  └── 法院认定: "接到通知后未提出异议" = 有效的默示授权           │  │
│  │                                                                │  │
│  │  同时通过企微/钉钉发送相同内容(多渠道送达, 增加触达率)           │  │
│  │                                                                │  │
│  │                                                                │  │
│  │  ═══ 第三层: 司机身份采集 (仓库现场) ═══                       │  │
│  │                                                                │  │
│  │  仓库发货前必须采集司机身份信息:                                 │  │
│  │                                                                │  │
│  │  ├── 必采信息:                                                 │  │
│  │  │   ├── 司机姓名、手机号                                      │  │
│  │  │   ├── 车牌号                                                │  │
│  │  │   ├── 身份证照片(正面拍照)                                  │  │
│  │  │   └── 司机人脸照片(现场拍摄, 非翻拍)                        │  │
│  │  │                                                             │  │
│  │  ├── 可选信息:                                                 │  │
│  │  │   ├── 驾驶证照片                                            │  │
│  │  │   ├── 行驶证照片                                            │  │
│  │  │   └── 授权委托书照片(如司机随身携带)                         │  │
│  │  │                                                             │  │
│  │  ├── 与预登记比对:                                             │  │
│  │  │   ├── 如司机在预登记名单中 → 自动通过 + 标记"已授权人员"     │  │
│  │  │   └── 如司机不在名单中 → 标记"未预登记" + 触发电话确认       │  │
│  │  │                                                             │  │
│  │  └── 照片要求:                                                 │  │
│  │      ├── 强制 GPS 水印 + 时间水印                              │  │
│  │      ├── 活体检测(H5/WMS拍摄, 非相册选图)                      │  │
│  │      └── 照片上传后不可删除/修改                                │  │
│  │                                                                │  │
│  │  证据效力:                                                     │  │
│  │  ├── 身份证+人脸 = 确认了"谁来提的货"                          │  │
│  │  ├── 如果与预登记匹配 = "客户事先授权了此人"                    │  │
│  │  └── 即使客户否认"不认识此人", 身份信息+预登记记录可反驳        │  │
│  │                                                                │  │
│  │                                                                │  │
│  │  ═══ 第四层: 电话确认 (未预登记司机触发) ═══                    │  │
│  │                                                                │  │
│  │  当提货司机不在预登记名单中时:                                   │  │
│  │  ├── 系统自动拨打客户登记手机号(IVR自动语音):                    │  │
│  │  │   "您好，XX仓库有人以您的名义提货，提货人[王五]，             │  │
│  │  │    车牌[沪A12345]，请按1确认，按2拒绝。"                     │  │
│  │  ├── 客户按1 → 录音存证 → 允许提货                             │  │
│  │  ├── 客户按2 → 录音存证 → 拒绝提货 + 通知仓库停止              │  │
│  │  ├── 客户未接听(3次) → 记录未接记录 → 转人工(仓库电话联系)      │  │
│  │  │   仓库人工电话确认 → 通话录音 → 允许/拒绝                    │  │
│  │  └── 紧急情况: 联系销售员确认                                   │  │
│  │                                                                │  │
│  │  IVR 通话录音 = 强证据(客户亲口确认"是我安排的")                │  │
│  │                                                                │  │
│  │  对于已预登记的司机:                                            │  │
│  │  ├── 不触发电话确认(不打扰客户)                                 │  │
│  │  └── 仅发送确权短信(第二层)                                     │  │
│  │                                                                │  │
│  │                                                                │  │
│  │  ═══ 第五层: 交易习惯证据 (系统自动积累) ═══                   │  │
│  │                                                                │  │
│  │  系统自动建立每个客户的提货行为画像:                              │  │
│  │  ├── 历史提货人清单 (哪些司机曾为该客户提货)                     │  │
│  │  ├── 每个司机的提货次数和金额                                   │  │
│  │  ├── 客户对每次提货的确认/付款记录                              │  │
│  │  ├── 客户从未对任何一次提货提出否认                              │  │
│  │  └── 同一司机+同一客户的连续交易记录                            │  │
│  │                                                                │  │
│  │  法律论证:                                                     │  │
│  │  ├── "该司机曾为该客户提货47次, 客户均已付款, 从未否认"         │  │
│  │  ├── "第48次提货模式完全一致, 客户突然声称不认识此人,            │  │
│  │  │    明显不符合交易习惯, 有逃避债务之嫌"                       │  │
│  │  └── 《民法典》第142条: 应按照交易习惯确定当事人意思表示         │  │
│  │                                                                │  │
│  │  系统自动生成《交易习惯报告》:                                   │  │
│  │  ├── 客户与该司机的历史合作统计                                 │  │
│  │  ├── 客户历次提货的确认/付款时间线                              │  │
│  │  ├── 异常提货(被客户否认)的占比                                 │  │
│  │  └── 可导出为 PDF 用于诉讼举证                                 │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  ┌─── 五层证据叠加效果 ──────────────────────────────────────────┐  │
│  │                                                                │  │
│  │  场景: 客户否认"我没派人去提货"                                 │  │
│  │                                                                │  │
│  │  卖方出示:                                                     │  │
│  │  ├── 证据1: 客户在系统中预登记了司机王五为授权提货人             │  │
│  │  │         (登记时间/IP/设备记录)                               │  │
│  │  ├── 证据2: 提货当天系统发送了确权短信, 客户收到未否认          │  │
│  │  │         (运营商送达回执 + 客户点击查看记录)                   │  │
│  │  ├── 证据3: 仓库采集了司机身份证+人脸照片, 与预登记信息一致     │  │
│  │  │         (照片含GPS+时间水印)                                │  │
│  │  ├── 证据4: 系统拨打了客户电话, 客户按"1"确认了提货             │  │
│  │  │         (IVR通话录音)                                       │  │
│  │  └── 证据5: 该司机此前已为该客户提货47次, 客户均已付款          │  │
│  │            (《交易习惯报告》)                                   │  │
│  │                                                                │  │
│  │  法院认定: 五项证据形成完整证据链, 足以证明客户授权提货          │  │
│  │  客户抗辩: 不成立                                               │  │
│  │                                                                │  │
│  │  注意: 并非每次提货都需要五层全部具备                            │  │
│  │  ├── 最低保障: 第二层(确权短信) + 第三层(身份采集)              │  │
│  │  ├── 标准保障: 第一层 + 第二层 + 第三层                        │  │
│  │  └── 最高保障: 五层全部 (高风险客户/大额提货)                   │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  ┌─── 确权强度自动分级 ──────────────────────────────────────────┐  │
│  │                                                                │  │
│  │  系统根据客户风险等级自动调整确权强度:                            │  │
│  │                                                                │  │
│  │  ┌────────────────────────────────────────────────┐            │  │
│  │  │ 客户信用评分  │ 确权强度          │ 触发的层级    │            │  │
│  │  │──────────── ┼ ──────────────── ┼ ──────────── │            │  │
│  │  │ A级(优质)    │ 轻度(不打扰)      │ 2+3           │            │  │
│  │  │ B级(良好)    │ 标准             │ 1+2+3         │            │  │
│  │  │ C级(一般)    │ 加强             │ 1+2+3+4       │            │  │
│  │  │ D级(风险)    │ 严格             │ 1+2+3+4+5     │            │  │
│  │  │ E级(高危)    │ 最严格            │ 全部五层+人工  │            │  │
│  │  │ 新客户       │ 加强             │ 1+2+3+4       │            │  │
│  │  │ 首次司机     │ 加强(不论客户等级) │ +电话确认      │            │  │
│  │  │ 单次>50万    │ 加强(不论客户等级) │ +电话确认      │            │  │
│  │  └────────────────────────────────────────────────┘            │  │
│  │                                                                │  │
│  │  与 AutoRecon 信用评分联动:                                     │  │
│  │  客户信用评分越低 → 确权越严格 → 证据越充分                     │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  ┌─── 不增加客户负担的设计要点 ──────────────────────────────────┐  │
│  │                                                                │  │
│  │  对于优质老客户 (A/B级):                                       │  │
│  │  ├── 预登记了常用司机 → 司机来了直接提 → 客户只收到一条短信     │  │
│  │  ├── 不打电话、不要求确认、不阻塞任何流程                       │  │
│  │  └── 体验与之前完全一致                                        │  │
│  │                                                                │  │
│  │  对于新客户/风险客户 (C/D/E级):                                 │  │
│  │  ├── 首次提货会打一个电话确认(30秒, 按1即可)                   │  │
│  │  ├── 以后同一司机再来 → 不再电话确认(已建立信任)                │  │
│  │  └── 客户感受: "第一次确认了一下，以后就不用了"                  │  │
│  │                                                                │  │
│  │  核心: 确权力度与客户信任度反比                                  │  │
│  │  信任越高 → 流程越轻 → 客户越不受打扰                           │  │
│  │  信任越低 → 流程越严 → 证据越充分                               │  │
│  └────────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
```

#### 4.2.4 法律效力总结（含确权后的完整证据链）

```
┌──────────────────────────────────────────────────────────────────────┐
│              留货合同完整证据效力 (客户否认时的举证能力)                │
│                                                                      │
│  证据层级    │ 证据内容                 │ 采集方式      │ 法律效力    │
│  ─────────┼─────────────────────── ┼ ──────────── ┼ ────────── │
│  合同依据    │ ERP合同(双方确认的交易)   │ ERP自动同步   │ ★★★★      │
│  提货人授权  │ 客户预登记的提货人名单    │ 客户/销售录入 │ ★★★★★    │
│  实时确权    │ 确权短信+送达回执         │ 系统自动发送  │ ★★★★      │
│  电话录音    │ IVR客户语音确认录音      │ 系统自动拨打   │ ★★★★★    │
│  身份采集    │ 司机身份证+人脸照片      │ 仓库现场拍摄   │ ★★★★      │
│  发货过程    │ 逐吊明细+操作员记录      │ WMS/H5/驾驶员 │ ★★★★      │
│  现场影像    │ 装车照+货物照+车牌照      │ 仓库拍摄      │ ★★★       │
```

#### 4.2.6 合同模板引擎设计

##### 问题分析

```
不同商家对合同的需求差异极大:

├── 商家A(大型钢贸商): 合同内容详尽, 有法务审核, 条款严谨
├── 商家B(中型贸易商): 合同简洁, 只关注品规/价格/付款
├── 商家C(钢厂直销):  有标准格式, 不愿改动自有模板
└── 商家D(小型商户):  没有合同模板, 希望平台提供标准版

同一商家不同合同类型也不同:
├── 留货合同: 侧重品规/批号/仓位/提货期
├── 订货合同: 侧重交货期/质量标准/验收条件
└── 长期框架协议: 侧重定价机制/年度用量/结算方式

平台防变动条款如何融入:
├── 方案A: 强制嵌入商家合同正文 → 商家不接受(破坏他们的合同格式)
├── 方案B: 作为独立附件 → 客户可能不看
└── 方案C: 分层设计(商家正文 + 平台通用条款) → 最佳方案 ✓
```

##### 平台交易服务条款 — 作为合同附件自动附加

```
│                                                                      │
│  条款附加规则:                                                       │
│  ├── 自动附加: 生成合同PDF时系统自动拼接, 无需商家手动操作            │
│  ├── 不可删除: 商家不能跳过此附件(平台风控底线)                      │

│  │   └── 附件优先: 适合小商家(平台条款比他们的更规范)              │
│  ├── 客户看到: 合同正文 + 附件一起展示, 签章覆盖全部               │

│  ├── 如: "本合同项下货物如需退货, 需在提货后7天内提出"               │
```

```
│  │  ├── 到期前提醒: 到期前 N 小时再发一次提醒短信(可配置)          │  │
│  │  └── 配置值自动写入合同: 商家改配置 → 新合同自动用新时限        │  │
│  │      (已签合同按签署时的配置执行, 不受后续修改影响)              │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  ┌─── 提货确认单法律效力 ────────────────────────────────────────┐  │
│  │                                                                │  │
│  │  三重保障:                                                      │  │
│  │                                                                │  │
│  │  1. 框架合同签章 (已有) → 确立"以实发为准"的规则                 │  │
│  │  2. 提货确认单签字 (仓库+司机) → 确认"实际发了什么"              │  │
│  │  3. 客户事后确认/默认确认 → 确认"客户认可实际结果"               │  │
│  │                                                                │  │
│  │  即使客户事后否认:                                               │  │
│  │  ├── 框架合同中约定了"以实发为准" → 客户已签章同意此规则          │  │
│  │  ├── 品规变更已通知 + 客户未在约定时限内异议 → 默示确认          │  │
│  │  ├── 提货确认单有司机签字 + 仓库签字 → 双方现场确认              │  │
│  │  └── 全部通知+送达记录可追溯 → 不存在"不知情"                   │  │
│  └────────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
```

#### 4.2.8 留货合同和订货合同的变动处理对比

| 场景 | 留货合同处理 | 订货合同处理 |
|------|------------|------------|
| **品规变更** (仓库调整) | 框架合同允许+提货确认单记录+通知客户24h确认 | 同左 |
| **数量变更** (库存/产量原因) | 实发为准+提货确认单记录+容差内正常/超差通知 | 同左 |
| **重量偏差** (过磅vs理论) | 框架合同约定±3%容差+以过磅为准 | 同左 |
| **价格变动** (品规变更导致) | 按框架合同定价规则+变更品规对应价格 | 同左 |
| **多提/少提** | 以实际提货为准+提货确认单+差异通知 | 以实际到货为准+差异通知 |
| **客户不确认** | 通知后N天默认确认(合同约定) | 同左 |
| **客户提异议** | 进入异议处理流程(与对账系统联动) | 同左 |

#### 4.2.9 订货合同 — 主动签约模式

订货合同同样采用"框架合同+提货确认单"架构。签约环节保留（涉及生产/采购安排），但合同条款同样约定"以实发为准"。

```
┌──────────────────────────────────────────────────────────────────────┐
│               订货合同 — 主动签约 + 以实发为准                         │
│                                                                      │
│  ERP合同生效                                                         │
│      │                                                               │
│      ▼                                                               │
│  系统生成框架合同 (含标准防变动条款)                                    │
│  ├── 预估品规/数量(标注"预计")                                       │
│  ├── 定价规则/付款条件/交货期                                        │
│  ├── "实际交货以提货确认单为准"条款                                   │
│  ├── 数量/品规变更通知与确认条款                                      │
│  └── 重量以过磅为准 + ±3%容差条款                                    │
│      │                                                               │
│      ▼                                                               │
│  推送客户签约 (含标准条款) → 客户签章确认                              │

│                                                                      │
│  变动举例:                                                            │
│  ├── 合同预估500吨，钢厂实际产出487吨 → 以487吨结算 → 合法合规        │
```

#### 4.2.10 两种合同模式对比

| 维度 | 留货合同(静默模式) | 订货合同(主动模式) |
|------|------------------|------------------|
| **客户操作量** | **零操作(全部可选)** | 需签约确认 |
| 签约 | 可选增强，不阻塞提货 | 必须，阻塞生产/采购 |
| 派车 | 不需要，司机直接去 | 需要(可客户/销售/承运) |
| 提货触发 | 仓库端发起(司机到了就开始) | 提货单生成后发起 |
| 提货单生成 | 仓库发货时自动创建 | 派车确认后预先创建 |
| 提货码 | 可选(仓库验证客户+合同号即可) | 必须(凭码提货) |
| 证据采集 | 仓库端静默采集 | 全流程主动采集 |
| 客户通知 | 事后通知(提完货告诉客户) | 事前+过程+事后全程通知 |
| 客户确认 | 可选，不确认也有效 | 需要(可超时自动确认) |
| 适用场景 | 老客户、长期合作、重复采购 | 新客户、大额订单、定制品 |

### 4.6 阶段五：仓库发货（多模式适配 — 有 WMS 与无 WMS）

#### 4.6.1 问题分析

并非所有仓库都部署了自有 WMS 系统。实际场景中仓库类型多样：

| 仓库类型 | 占比(估) | 系统现状 | 发货方式 |
|---------|---------|---------|---------|
| 自有仓库（已部署 WMS） | ~35% | 有 Android WMS | 系统化逐吊发货 |
| 自有仓库（无 WMS） | ~20% | 纸质单据 + 手工记账 | 人工记录 |
| 第三方仓储 | ~25% | 有自己的 WMS | 第三方系统出库 |
| 合作钢厂直发 | ~15% | 钢厂自有系统 | 钢厂安排发货 |
| 临时堆场/工地 | ~5% | 无任何系统 | 完全手工 |

**设计原则**: 不管仓库有没有 WMS，发货环节都必须产出可追溯的证据。

#### 4.6.2 五种发货模式

## 七、合同状态机（按合同类型差异化）

### 7.1 留货合同状态机（静默模式）

```
                    ┌──────────┐
     ERP同步 ──→    │  可提货   │ ←── 留货合同同步后直接进入可提货状态
                    │ READY    │     无需签约即可提货
                    └────┬─────┘
                         │
              ┌──────────┼──────────┐
              │          │          │
       仓库发货     客户主动签约    超期未提
       (司机到了)    (可选增强)     │
              │          │          ▼
              │          │    ┌──────────┐
              │          │    │ 超期预警  │
              │          │    │ OVERDUE  │
              │          │    └──────────┘
              │          │
              ▼          │
      ┌──────────┐       │
      │  提货中   │←──────┘ (签约不阻塞提货)
      │ PICKING  │ ←── 可多次提货(部分提货)
      └────┬─────┘
           │ 全部提完
           ▼
      ┌──────────┐
      │  已提完   │
      │ PICKED   │
      └────┬─────┘
           │ 全部结清
           ▼
      ┌──────────┐
      │  已结清   │
      │ SETTLED  │
      └──────────┘

  签约状态(独立于合同主状态):
  ├── 未签约: 不影响提货，证据靠仓库采集
  ├── 已签约: 增强证据效力
  └── 签约标记在 sign_status 字段，不影响合同主状态流转
```

### 7.2 订货合同状态机（主动模式）

```
                    ┌──────────┐
     ERP同步 ──→    │  待签约   │
                    │PENDING   │
                    │_SIGN     │
                    └────┬─────┘
                         │ 推送给客户签约
                         ▼
                    ┌──────────┐
                    │  签约中   │
            ┌──────│ SIGNING  │──────┐
            │      └──────────┘      │
            │                        │
     客户签署完成               客户拒签

            │                       │
            ▼                       ▼
      ┌──────────┐           ┌──────────┐
      │  已签约   │           │  已拒签   │
      │ SIGNED   │           │ REJECTED │
      └────┬─────┘           └──────────┘
           │ 客户发起提货(或到货通知)
           ▼
      ┌──────────┐
      │  提货中   │ ←── 可多次提货
      │ PICKING  │
      └────┬─────┘
           │ 全部提完
           ▼
      ┌──────────┐
      │  已提完   │
      │ PICKED   │
      └────┬─────┘
           │ 全部结清
           ▼
      ┌──────────┐
      │  已结清   │
      │ SETTLED  │
      └──────────┘
```

## 十二、安全设计

| 维度 | 措施 |
|------|------|
| 提货码安全 | 加密生成(SecureRandom)、一次性使用、有效期限制、暴力猜测防护(5次错误锁定) |
| API认证 | 各端使用不同的认证方式: PC/H5用JWT、小程序用微信授权+Token、WMS用设备证书+Token |
| 数据传输 | 全链路HTTPS、WMS离线数据本地AES加密 |
| 证据防篡改 | 每条证据生成时计算SHA-256哈希、证据包整体哈希、定期校验 |
| 照片防伪 | 照片嵌入GPS水印+时间水印+设备信息，防截图替换 |
| 操作审计 | 全操作日志，保留期≥5年(证据相关保留≥10年) |
| 签名安全 | 电子签名使用第三方签章服务，驾驶员/操作员签名记录设备指纹 |

## 十五、买方零阻力参与设计

### 15.1 问题的特殊性

```
证据链系统比对账系统更难推广给买方:

对账系统: "帮你对账更方便" → 买方能感知到好处
证据链系统: "记录你提了多少货" → 买方觉得"你在收集证据告我"

买方内心独白:
├── "你搞这套东西，是不是就等着以后告我？"
├── "我配合你搞证据链，等于帮你准备打官司的材料"
├── "以前提货很简单，现在搞得这么复杂"
├── "我又不欠你钱，搞这些干嘛"
└── "太麻烦了，我换一家供应商"

核心矛盾: 证据链对卖方的价值(追款有据) = 买方眼中的威胁(被追款)
```

### 15.2 设计总原则

```
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│  原则一: 证据链系统对买方"不存在"                                 │
│  ├── 买方看到的不是"证据链系统"                                   │
│  ├── 买方看到的是"供应商给我发了提货通知/结算通知"                 │
│  └── 系统名称在买方侧: "供应链服务平台" 而非 "欠款证据链"         │
│                                                                  │
│  原则二: 所有证据采集不依赖买方操作                                │
│  ├── 100%的证据可以在买方零参与的情况下采集完成                    │
│  ├── 买方参与只是"增强证据效力"，不是"必要条件"                   │
│  └── 系统已通过仓库端+驾驶员端+通知送达完成全部证据采集            │
│                                                                  │
│  原则三: 对买方只展示"对他有价值的功能"                            │
│  ├── 买方看到: 合同查询、提货进度、结算明细                       │
│  ├── 买方看不到: 证据包、证据归档、交易习惯报告                   │
│  └── 功能命名: "我的订单"而非"证据追踪"                           │
│                                                                  │
│  原则四: 买方的每次互动都有即时回报                                │
│  ├── 查看提货进度 → 实时知道货到哪了/装了多少                     │
│  ├── 查看结算单 → 清楚知道欠了多少钱、什么时候该付                │
│  └── 确认提货 → 避免被人冒名提货(保护买方自身利益)                │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

```
┌──────────────────────────────────────────────────────────────────┐
```

### 15.4 买方四级参与模型（与对账系统一致）

```
┌─────────────────────────────────────────────────────────────────┐
│              买方参与度四级模型 (证据链版)                        │
│                                                                 │
│  Level 0: 纯被动接收 ←── 买方什么都不用做                       │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ │

│  │ 短信中包含链接, 买方好奇/想看货提了多少→点击链接               │
│  │ 不需要注册→直接查看提货单/结算单                              │

│  │                                                              │

│  ▼                                                              │

│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ │
```

### 15.7 买方不同态度的应对策略

| 买方态度 | 表现 | 系统应对 | 证据保障 |
|---------|------|---------|---------|
| **完全无视** | 不点链接、不接电话、不回短信 | Level 0 长期保持，仓库端采集全部证据 | 9 项基础证据 + 短信送达回执 + 默认确认 |
| **偶尔看看** | 有时点开短信链接看一下 | 记录每次查看行为 → Level 1 | 基础证据 + 知情证据(IP/时间) |
| **嫌烦但配合** | 觉得电话烦，愿意登记司机 | 登记后不再电话打扰 → Level 2 | 基础证据 + 授权证据 |
| **主动使用** | 查进度、看账单、自己派车 | 引导注册、提供增值功能 → Level 2-3 | 基础证据 + 全部增强证据 |

| **怀疑动机** | "你是不是要告我" | 用话术四解释 + 展示对买方的保护价值 | 基础证据 |

```yaml
pickup-express:
```

```typescript
import { createPickupExpress } from 'pickup-express-web'
app.use(createPickupExpress({
```
